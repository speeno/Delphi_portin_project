# 거래처코드 7자(`A000001`) 확장 — 영향 조사 (결론: **미진행**)

> **결정 (2026-09-08 사용자)** — 「기존 코드 체계 유지해주세요」.
> 레거시 스키마는 손대지 않는다. 거래처코드는 현행 **접두 1자 + 4자리 = 5자**(`A0001`) 그대로.
> 아래 조사 내용은 «나중에 같은 요청이 다시 올 때» 재조사하지 않기 위한 기록이다.

- 요청: 2026-09-08 사용자 「신규 출판프로그램 반영 요청 건」 참고 이미지 — 거래처구분별 접두 +
  **6자리 일련번호**(`A000001` … `K000001`).
- 현행: 접두 + 4자리(`A0001`). 레거시 `G1_Ggeo.Gcode` 가 **varchar(5)** 이기 때문(DEC-262).
- 이 문서는 "7자로 넓히려면 무엇을 건드려야 하는가"의 **실측 조사 결과**다. 스키마 변경은
  아직 하지 않았다 — 착수 여부는 사용자 승인 사항.
- 관련: DEC-262(코드 폭 가드·잘림 사고), DEC-267(구분 순서·매칭), DEC-079(접두 채번 스킴).

## 2. 확장 시 위험

1. **무중단 불가** — MySQL 3.23/5.1 의 `ALTER TABLE … MODIFY` 는 테이블 전체 재작성 + 쓰기 잠금.
   `S1_Ssub`(2,375만 행)는 수십 분 이상 잠길 수 있고 그동안 **델파이 프로그램과 웹이 함께 정지**한다.
   → 야간 점검 창 필수.
2. **작업량** — (테넌트 DB 약 50+) × (거래처코드 컬럼 다수). 스크립트화 + 진행/롤백 로그 필요.
3. **델파이 영향** — `.dfm` 에 `MaxLength` 지정이 없다(TField.Size 상속). 컬럼을 넓히면 델파이
   입력칸도 자동으로 7자를 받는다. 다만 고정폭 명세서·리포트 정렬은 육안 확인이 필요하다.
   `.pas` 에서 `Copy(Gcode,1,5)` / `Length(Gcode)=5` 류 하드코딩은 1차 grep 에서 **발견되지 않음**
   (정밀 검사는 Phase 0).
4. **웹 코드 변경은 0** — 채번·입력 maxLength 는 이미 `SHOW COLUMNS` 실측 폭에서 산출한다(DEC-262).
   컬럼을 넓히면 자동으로 `A000001` 채번이 된다.
5. **혼재** — 기존 5자 코드(숫자 코드 포함)와 신규 7자 코드가 공존한다. 기존 코드를 새 체계로
   일괄 변환하려면 전표·원장의 참조까지 함께 갱신해야 하므로 **별도 프로젝트**로 본다.

## 3. 권고 절차(승인 시)

- **Phase 0 (조사 마무리)** — 154/155 접속 복구 후 폭 실측 · 45개 컬럼 중 「거래처코드」 컬럼 확정 ·
  테넌트 DB 별 행수/용량 측정 · 델파이 `.pas` 정밀 검사 · ALTER 소요시간 파일럿 측정.
- **Phase 1 (파일럿)** — 소규모 테넌트 1곳(예: chul_05_db)에서 야간 점검 창에 ALTER →
  델파이(입력·조회·명세서 인쇄) + 웹 회귀 확인. 사전 덤프 백업, 실패 시 원복.
- **Phase 2 (순차 전개)** — 테넌트 DB 단위로 야간 배치. 각 회차 후 델파이 현장 확인.
- **Phase 3 (채번 전환)** — 폭이 7이 되는 순간 자동으로 `A000001` 채번. 웹 배포 불필요.

## 4. 대안 — 5자 유지(`A0001`)

- 교문사(hcode 5019) 거래처 **1,299개**, 구분별 최대 673개. 접두 스킴은 **구분당 9,999개**를 주므로
  현 사용량 기준 수십 년 여유다.
- 구분↔접두 규칙(A~K, I 제외)은 요청 이미지와 **동일**하게 이미 동작한다(DEC-267 확인).
- 레거시 DB·델파이 무변경, 무중단, 위험 0.
