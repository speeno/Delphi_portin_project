# UI 레이아웃 통일·키보드 업무 흐름 개선 실행 프롬프트

작성일: 2026-09-11
문서 버전: 2 — 엔진 독립 실행·인수인계용
상태: 이 대화에서 수행한 작업은 조사와 문서 작성·보강이다. 이 대화를 통해 제품 코드는 수정하지 않았다. 이후 다른 작업자가 변경했을 수 있으므로 실행 시 Git 상태와 실제 구현을 재확인한다.

이 문서는 이전 대화, 특정 LLM의 메모리·스킬·플러그인 없이 읽을 수 있는 실행 명세다. 파일 접근·편집·셸·브라우저 기능은 사용하는 엔진의 동등한 도구로 대체한다. 도구가 없는 환경에서는 수행하지 못한 작업을 명시하고 검토 가능한 패치·절차를 제공한다. 도구 호출이나 실제 검증 결과를 만들어내지 않는다.

## 사용 방법

다음 요청과 함께 이 문서를 실행 에이전트에 전달한다.

> `docs/ui-layout-keyboard-improvement-prompt.md`를 기준으로 UI 개선을 실행해줘. 현재 코드와 지침을 다시 확인하고, 기존 키보드 업무 흐름을 보존하면서 공통 요소와 대표 조회·입력 화면에 먼저 적용해줘. 변경 및 검증 결과와 후속 적용 범위를 기록해줘.

기본 실행 범위는 아래 0~2단계의 공통 요소 및 대표 화면 한 쌍이다. 전체 화면 확대는 요청 범위에 포함된 경우 수행한다. 문서 열람만으로 구현·배포를 시작하지 않는다.

### 다른 엔진에 그대로 전달할 시작 요청

```text
당신은 기존 Delphi 도서물류 시스템을 웹으로 전환한 제품의 UI 개선 담당자다.
첨부한 ui-layout-keyboard-improvement-prompt.md 전체를 작업 명세로 사용하라.
이전 대화는 없다고 가정하라. 프로젝트 루트를 탐색해 제품 저장소를 확인하고,
현행 지침·코드·사용자 변경을 먼저 읽은 후 기본 실행 범위 0~2단계를 완료하라.
비고 Enter의 새 행 추가, 기존 키보드 입력 순서, 연속 전표 입력을 반드시 보존하라.
이미 있는 공통 레이아웃을 재사용하고, 키보드 결함만 수정한 뒤 레이아웃 작업을
완료했다고 보고하지 마라. 검증이 불가능한 항목은 미검증으로 구분하라.
로컬 변경과 검증을 수행하되 배포·운영 데이터 변경·인증 우회는 포함하지 마라.
현재 진행 상황과 검증 결과를 문서로 남겨 다른 작업자가 이어받을 수 있게 하라.
```

사용자는 범위·대표 화면·대상 브라우저·테스트 환경을 추가로 지정할 수 있다. 지정하지 않은 값은 아래 기본값으로 시작하고 확인할 수 없는 환경 정보만 미확정으로 기록한다. 기존 승인 범위의 일반적인 구현 선택을 매번 재질문하지 않는다.

| 실행 입력 | 기본값 또는 확인 방식 |
| --- | --- |
| 프로젝트 루트 | 현재 작업 디렉터리에서 README와 제품 디렉터리를 찾아 결정 |
| 기본 대표 화면 | `/transactions/sales-statement`와 `/transactions/sales-statement/new` |

| 구현 범위 | 0~2단계. 전체 화면 개편·다중 창 구조 재설계는 기본 범위 밖 |
| 검증 계정·데이터 | 현재 환경에서 허용된 테스트 계정·테스트 데이터만 사용. 제공되지 않은 자격 증명은 추정하지 않음 |
| 산출물 언어 | 사용자 안내·문서·결과 보고는 한국어 |

## 목표와 대상

기존 Delphi 프로그램의 숙련 사용자가 익숙한 키 입력 순서로 업무를 마칠 수 있도록 유지하면서 화면의 배치·표현·상태 안내를 통일한다.

- 제품 코드: `도서물류관리프로그램/frontend`.
- 루트 `frontend`와 샘플 디렉터리는 제품 코드와 혼동하지 않는다. 현재 README의 저장소 역할을 재확인한다.
- 제품은 별도 Git 저장소이므로 제품 디렉터리에서 변경 상태를 확인한다.
- 참고 자료: `docs/Design.md`, `docs/design-gap-analysis.md`, 제품의 적용 가능한 `AGENTS.md`, 기존 디자인 결정 및 실제 코드.
- Next.js 관련 수정 전 설치된 버전의 `node_modules/next/dist/docs/`에서 관련 문서를 읽는다.
- 사용자 수정 사항을 보존하고 불필요한 파일 동기화·리팩터링·의존성 교체를 하지 않는다.

### 용어와 판단 순서

- **조회형**: 조건을 입력하고 기존 전표·재고 등의 목록을 읽는 화면.
- **입력형 / 전표**: 거래처와 여러 도서 행을 입력해 저장하는 업무 화면.
- **구분**: 각 도서 행의 업무 구분 값. 비고에서 새 행 추가 시 먼저 입력하는 칸.
- **지점·지사**: 화면·계정에 따라 필요한 필드. 통일을 이유로 없는 화면에 추가하지 않는다.
- **선택 행**: 상세 조회·업무 작업의 대상 행. **포커스 셀**: 현재 키 입력을 받는 칸. 둘은 다를 수 있다.
- **IME 조합**: 한글 글자를 만드는 중간 상태. 조합 확정 Enter를 업무 명령으로 중복 처리하지 않는다.
- **앱 탭**: 제품 내부의 업무 창 탭. 브라우저 자체 탭과 구분한다.
- **DEC-번호**: 저장소의 기존 결정 식별자. 숫자만으로 내용을 추정하지 말고 코드·문서에서 검색한다.

판단 순서: 실행 환경의 상위 지침 → 사용자의 최신 명시 지시 → 이 문서의 보존 요구사항 → 적용 가능한 저장소 지침·확정된 기존 결정 → 일반 디자인 권고. 현행 코드와 문서가 다르면 구현을 조사하고 차이를 기록한다. 실제 업무 의미가 불명확한 기능키나 파괴적 동작은 추정으로 바꾸지 말고 해당 항목만 보류하며 독립적인 작업은 계속한다.

### 저장소·기술 스택 지도

작성 환경의 허브 경로는 `/Users/speeno/Delphi_porting`이지만 다른 컴퓨터에 이 절대 경로를 강제하지 않는다. 아래에서 모든 `src/…`는 제품 프런트엔드 기준이다.

```text

      package.json / package-lock.json
```

확인 당시 `package.json`: Next.js `16.2.4`, React `19.2.4`, Tailwind CSS `^4`, TypeScript `^5`, Base UI `^1.4.0`, Zustand `^5.0.12`, react-grid-layout `^2.2.3`. 범위 표기는 설치 버전 보장이 아니다. 실행 시 잠금 파일·설치 버전을 확인하며 버전 업그레이드를 UI 개선에 섞지 않는다. `@/*`는 `src/*` 경로 별칭이다. Tailwind v4의 토큰·CSS 구조를 존중하고 별도 디자인 시스템을 새로 도입하지 않는다.

### 현재 레이아웃의 확정된 예외 — 일반 권고보다 먼저 확인

- `PageHeader`는 확인 당시 `filtersBelow=true`가 기본이며, 필터는 제목 아래 왼쪽부터 배치한다. `actions`는 제목 줄 오른쪽 끝을 유지한다(코드의 DEC-228/263). 따라서 “조회 → 액션”이라는 추상 순서 때문에 신규·엑셀 버튼을 필터 아래로 무조건 옮기지 않는다.
- 헤더는 화면 공간 효율을 위해 낮게 유지하며, 설명은 제목 툴팁으로 남기는 결정이 있다(DEC-211). 큰 제목·설명 문단을 추가해 표를 아래로 밀지 않는다.
- `SlipEntryLayout`은 입고·출고 신규에서 이미 공용이다(DEC-239). 입력 필드와 저장은 라인 카드의 최상단에 함께 배치한다(DEC-266). 별도 상단 저장 바를 만들거나 입력 필드를 카드 밖으로 꺼내지 않는다.
- `SlipEntryLayout`의 헤더에는 Enter 이동 범위가 이미 있다. 전체 골격에 Enter 핸들러를 추가해 라인 그리드의 새 행 동작과 중복시키지 않는다.
- `data-legacy-id`, `data-slot`, 기존 ID·키가 테스트·레거시 대응·스타일에 쓰일 수 있다. 제거·변경 전 사용처를 조사한다.
- `WindowBody`는 안정적인 식별 속성과 memo를 이용해 iframe 재로드를 방지한다. 창 이동·포커스·크기 변경 때 `key`나 `src`를 바꾸어 입력 상태를 초기화하지 않는다.
- 기존 테마와 활성 라임색을 유지하는 방향이다. 기본 CSS 주석의 색상 설명만 믿지 말고 테마 override가 적용된 실제 색상을 측정한다.

## 반드시 보존할 사용자 요구사항

1. **비고에서 Enter로 새 행을 추가하고 새 행의 구분 칸으로 이동하는 동작은 의도된 기능이다. 삭제하거나 일반적인 다음 칸 이동으로 바꾸지 않는다.**
2. 한글 조합을 확정하는 Enter와 업무 명령 Enter를 구분한다. 조합 중에는 글자 확정만 하고, 조합 종료 후 정상 Enter의 기존 동작은 유지한다.
3. 기존 Enter 입력 순서, 방향키 이동, 값 전체 선택, 검색 결과 선택 후 다음 칸 이동을 보존한다.
4. 저장 후 날짜 유지·거래처 칸 복귀 등 연속 전표 입력 흐름을 보존한다.
5. 기존 업무 용어, 여러 자료를 비교하는 다중 창, 고밀도 표를 유지한다.
6. 정상적인 반복 입력·저장에 불필요한 확인창을 추가하지 않는다. 미저장 작업 이탈이나 위험 행동에만 필요한 보호를 적용한다.
7. 실제 레거시 대응을 확인하지 않고 F2 등을 전 화면의 동일 명령으로 재정의하지 않는다.
8. UI 통일을 이유로 업무 계산·API 계약·권한·데이터 범위·인쇄 결과를 변경하지 않는다.

## 화면 유형별 레이아웃 기준

모든 화면을 하나의 틀로 강제하지 않는다. 아래 순서는 시각적 그룹화 기준이며 기존 키보드 입력 순서를 임의 변경할 근거가 아니다.

| 유형 | 구성 기준 | 보존할 흐름 |
| --- | --- | --- |
| 조회형 | 제목 → 조회 조건 → 조회·초기화 → 결과 건수 → 표 → 합계·페이지 이동 | 조건 입력, Enter 조회, 결과 선택 후 상세 진입 |
| 입력형 | 제목·저장 상태 → 전표 기본정보 → 상세 입력 표 → 합계·보조정보 | 거래처·도서 입력, 수정, 새 행 추가, 저장 후 다음 전표 |
| 대시보드형 | 주요 업무 현황 → 처리할 항목 → 보조 정보 | 자주 쓰는 업무로 빠른 진입 |

### 공통 표현 규칙

- 조회 조건: 같은 의미의 필드는 화면군 내 명칭·폭·배치를 통일한다. 기존 순서와 차이가 나면 영향과 선택 근거를 기록한다.
- 버튼: 조회·신규·저장·인쇄·내보내기를 일정한 위치와 표현으로 제공한다. 삭제는 별도 그룹으로 구분한다. 실제 지원하는 단축키만 표시한다.
- 표: 헤더·행 높이, 테두리, 숫자 우측 정렬, 날짜·금액 형식, 합계 표현을 통일한다. 기존 틀 고정·정렬·열 설정·내보내기를 보존한다.
- 밀도: 현재 업무 정보량을 유지하는 밀도가 기본이다. 여백·글자 크기를 일괄 확대하지 않는다. 편안한 보기 옵션은 필요와 영향 확인 후 추가한다.
- 색상: 기존 테마 토큰을 사용한다. 활성 화면·선택 행·입력 포커스·오류를 구별한다. 포커스는 배경색뿐 아니라 선명한 테두리로 표시한다.
- 상태: 조회 전·조회 중·검색 결과 없음·등록 데이터 없음·실패를 구분한다. 저장 성공 메시지는 포커스를 가져가지 않는다. 오류는 입력값을 보존하고 해결 행동을 안내한다.
- 기술 정보: HTTP 상태 등은 필요할 때 펼쳐볼 수 있게 하고 업무 안내를 먼저 제공한다.
- 검색 팝업: 검색칸 → 결과 목록 → 선택·취소로 구성한다. 취소하면 원래 입력칸, 선택하면 해당 화면이 정한 다음 입력칸으로 이동한다.
- 다중 창: 활성 창 표시와 탭 제목을 명확히 한다. 닫기 버튼은 키보드 포커스에서도 보이고 대상 화면명이 접근성 이름에 포함되게 한다.

## 키보드 동작 기준

- 처리 우선순위: 한글 조합 → 열린 자동완성 → 최상위 팝업 → 현재 입력 컨트롤·그리드 → 활성 업무 화면 → 앱 셸.
- 한 이벤트는 한 계층에서만 소비한다. 중첩 이벤트 처리와 기본 동작 차단을 검토한다.
- ESC는 가장 안쪽 상태 하나만 취소한다. 팝업 취소가 배경 화면 이탈로 이어지지 않아야 한다.
- 팝업이 열려 있을 때 배경 전표의 저장 단축키가 실행되지 않아야 한다.
- 저장 중 키 반복으로 같은 요청이 중복 전송되지 않아야 한다. 성공 시 연속 입력, 실패 시 수정·재시도가 가능해야 한다.
- 방향키로 셀을 이동하되 텍스트 편집·선택과 기존 숫자 입력 규약을 보존한다.
- Tab·Shift+Tab으로 모든 필요한 기능에 접근할 수 있어야 한다. 시각적 배열과 포커스 순서를 일치시킨다.
- 모달은 초기 포커스·내부 순환·닫은 후 복원을 보장한다. 중첩 모달에서는 최상위 모달만 키를 처리한다.
- 창을 전환하면 마지막 입력 위치로 복귀하도록 검토한다. iframe 내부 포커스와 활성 창의 명령 범위를 함께 확인한다.
- 브라우저·OS 예약키 충돌을 확인하고 지원할 수 없는 기존 키는 대안과 이유를 기록한다.

## 단계별 실행

### 실행 환경 준비와 명령 예시

아래는 표준 셸 예시이며 특정 LLM 도구 이름을 요구하지 않는다. 첫 블록은 허브 루트에서 실행한다. 경로의 한글·공백·괄호 때문에 파일 경로는 항상 인용한다. 없는 경로는 현재 위치에서 제한적으로 검색하고 사용자 홈 전체를 탐색하지 않는다.

```bash
pwd
git status --short
git -C "도서물류관리프로그램" status --short
rg --files -g AGENTS.md -g '!node_modules/**' -g '!**/node_modules/**'
cat "도서물류관리프로그램/frontend/AGENTS.md"
cat "도서물류관리프로그램/frontend/package.json"
git -C "도서물류관리프로그램" rev-parse HEAD
```

무시된 제품 폴더의 지침은 `rg` 결과에 없을 수 있어 직접 읽는다. 파일 검색에 `rg`가 없으면 동등한 파일 검색 도구를 사용한다. 초기 Git 상태와 기준 커밋을 기록하고 기존 변경은 되돌리지 않는다.

제품 프런트엔드 작업 디렉터리로 이동한 뒤:

```bash
cd "도서물류관리프로그램/frontend"
node --version
npm --version
cat "node_modules/next/dist/docs/01-app/03-api-reference/01-directives/use-client.md"
npm run typecheck
```

설치 문서가 없으면 현재 설치 위치를 검색한다. 패키지가 없을 때는 잠금 파일 기반 설치 절차와 네트워크 허용 범위를 확인한다. 전역 패키지 설치나 무조건적인 재설치를 하지 않는다.

개발 서버가 실행 중인지 먼저 확인한다. 없으면 프런트엔드 디렉터리에서 `npm run dev`를 실행하고 출력된 실제 URL·포트를 사용한다. `3000`은 기본 후보일 뿐 고정된 운영 주소가 아니다. 기존 서버를 종료하거나 임의로 백엔드 전체를 재시작하지 않는다.

API 연결은 `next.config.ts`에서 확인한다. 조사 당시 `/api/v1/*`는 `BLS_API_PROXY_TARGET`으로 프록시되며 기본 대상은 `http://127.0.0.1:8000`이다. `NEXT_PUBLIC_API_URL`이 지정되면 브라우저 직접 연결 경로가 될 수 있다. 서버가 로컬이어도 연결된 DB가 테스트 데이터라는 뜻은 아니다. `.env`·토큰·계정 정보 내용을 로그나 보고서에 복사하지 않는다. 백엔드 기동이 필요하면 제품의 현행 실행 지침을 읽고 테스트 연결임을 확인한다.

브라우저 접근 순서:

1. 허용된 계정으로 로그인하고 정상 메뉴를 통해 대표 화면에 진입한다.
2. 제품은 `/workspace?open=…` 및 내부 `?embed=1` iframe을 사용할 수 있다. 주소 경로만 보고 실제 본문이 top document에 있다고 가정하지 않는다.
3. 직접 임베드 화면에서의 검증과 셸 안에서의 검증을 구분한다. 팝업·단축키·창 전환은 셸에서도 확인한다.
4. 로그인 정보가 없으면 인증을 우회하지 않는다. 독립적인 정적 검토·타입 검사·컴포넌트 테스트를 진행하고 실제 업무 검증만 미완료로 기록한다.

### 이벤트 수정 시 구현 주의사항

- React 이벤트와 native `document/window` 리스너의 전파·등록 위치를 함께 확인한다. `stopPropagation()`만 추가하거나 `defaultPrevented`만 검사했다고 중첩 충돌이 모두 해결되는 것은 아니다.
- 동일 노드의 리스너 등록 순서에 의존하는 임시 수정을 피한다. 자동완성 선택 직후 팝업 상태가 바뀌는 경우도 검증한다.
- 조합 중 처리뿐 아니라 조합 종료 직전·직후의 실제 키 이벤트를 확인한다. 임의의 지연 타이머나 모든 Enter 차단으로 정상 반복 입력을 느리게 만들지 않는다.
- 컨테이너 Enter 이동은 자식 위젯이 처리한 명령을 다시 실행하지 않아야 한다. textarea 줄바꿈, readOnly 콤보, 비활성·숨김 칸 등 기존 예외를 유지한다.
- 비동기 도서 조회는 오래된 응답이 현재 입력·선택·포커스를 덮어쓰지 않아야 한다.
- 저장 버튼 비활성화만으로 키 반복·동시 클릭에 대한 중복 요청 방지가 보장된다고 가정하지 않는다. 요청 진행 상태와 모든 종료 경로를 확인한다.
- iframe 내부의 키는 부모 document로 일반 DOM 버블링되지 않는다. 창 간 키 처리가 필요하면 기존 구조부터 확인하고 전역 리스너 하나로 해결되었다고 판단하지 않는다.
- DOM 순서에 의존하는 이동 함수가 있으므로 CSS `order`만 바꿔 시각적 순서와 입력 순서가 다르게 만들지 않는다.
- 미저장 감지는 초기 로딩·기존 값 복원·저장 성공을 수정 상태로 오인하지 않아야 한다. 기본 범위에서는 관련 상태 구조를 무리하게 전면 개편하지 않는다.

### 0단계: 기준선 확인

1. 현재 저장소 상태·지침·기존 디자인 결정을 확인한다.
2. 대표 조회·입력 화면 한 쌍을 선정한다. 기본 후보는 거래명세서 목록과 신규 입력이며, 실제 업무 연결을 확인해 확정한다.
3. 변경 전 화면, 보이는 열·행 수, 입력 순서, 단축키, 저장 후 상태를 기록한다.
4. 각 개선 후보를 확인됨·미재현·이미 해결됨으로 분류한다.
5. 사용자 실데이터를 변경하지 않는 테스트 환경이나 테스트 데이터를 사용한다.

### 1단계: 공통 기반

- 기존 공통 표·버튼·테마를 이용해 표시 규칙과 포커스 표현을 통일한다.
- 재현된 한글·ESC·저장키 충돌을 수정한다. 키보드 동작 변경은 레이아웃 수정과 구분해 검토 가능하게 한다.
- 공통 컴포넌트 변경이 영향을 주는 대표 화면도 함께 확인한다.

### 2단계: 대표 화면 적용

- 조회 조건·작업 버튼·건수·합계·표의 배치를 화면 유형 기준에 맞춘다.
- 입력 순서와 새 행 추가·연속 입력을 보존한다.
- 검색 팝업·오류·저장 상태 안내까지 한 업무 흐름으로 검증한다.
- 변경 전후 차이, 검증 결과, 확대 시 주의사항을 보고한다.

### 3단계: 화면군 확대

- 전체 확대가 요청되었으면 조회형 → 입력형 → 검색 팝업·다중 창 → 대시보드 순으로 진행한다.
- 같은 공통 요소를 재사용하되 기존 업무 차이는 명시적인 예외로 남긴다.
- 미저장 초안 보호, 창별 포커스 복원처럼 상태 구조 변경이 필요한 항목은 별도 변경 단위로 수행한다.

## 검증 시나리오와 완료 기준

### 필수 업무 검증

1. 마우스 없이 거래처 조회 → 도서 여러 건 입력 → 수량 수정 → 비고 Enter 새 행 추가 → 저장 → 다음 전표 입력.
2. 한글 비고 조합 중 Enter는 글자 확정만 수행하고, 조합 종료 후 Enter는 정확히 한 번 새 행을 추가.
3. 검색 팝업에서 ↑↓·Enter로 선택 후 다음 칸 이동. ESC 취소 시 원래 칸 복귀와 배경 화면 유지.
4. 자동완성·팝업이 열린 상태에서 ESC·저장키·키 반복을 실행하여 배경 명령·중복 저장이 발생하지 않음.
5. 저장 실패 시 값 유지, 오류 수정·재시도 가능. 성공 후 날짜 유지·거래처 칸 복귀.
6. 창 전환, 열 숨김·재배치, 화면 폭 변경, 스크롤 후에도 현재 입력 위치를 식별하고 필요한 기능에 접근 가능.
7. 바코드 입력을 사용하는 대상 화면에서는 스캐너의 종결 Enter와 일반 입력 흐름도 검증.

### 품질 확인

- 변경 범위에 적합한 타입 검사·린트·기존 테스트를 실행한다. 이벤트 충돌·한글 조합·중복 저장에는 의미 있는 회귀 검증을 추가한다.
- 실제 대상 브라우저·한글 IME에서 수동 확인한다. 합성 키 이벤트 테스트만으로 실제 한글 입력 검증을 완료했다고 보고하지 않는다.
- 대표 화면을 실제 렌더링해 잘림·겹침·불필요한 스크롤·포커스 가림을 확인한다.
- 사용자 작업 시간·키 입력 횟수·마우스 사용 횟수·표시 정보량을 변경 전과 비교한다. 사용자 실측이 없으면 수치를 추정해 완료 결과로 제시하지 않는다.
- 일반 텍스트 대비 4.5:1 등 적용 가능한 접근성 기준을 확인한다. 목표 크기는 예외·간격 조건을 포함해 평가하며 일괄 확대하지 않는다.
- 실행하지 못한 검증은 사유와 후속 확인 절차를 기록한다. 제품 적용·사용자 검증·배포 완료를 서로 구분한다.

### 구체적인 검사 실행 예시

아래 명령은 실행할 엔진이 사용하는 셸에서 수행한다. 이 문서의 명령이 존재한다는 사실은 통과 증거가 아니다.

제품 프런트엔드 디렉터리:

```bash
npm run typecheck
npm run lint -- "src/components/shared/page-header.tsx" "src/components/transactions/slip-entry-layout.tsx"
```

린트 인자는 실제 변경한 파일 목록으로 바꾼다. 기존 오류와 이번 변경으로 발생한 오류를 구분하고 검사를 약화하거나 관련 없는 오류를 대량 수정하지 않는다. `npm run build`가 필요하면 `prebuild`가 `scripts/write-version.mjs`를 실행한다는 점을 확인하고 생성된 파일의 diff를 검토한다. 레이아웃 작업마다 프로덕션 빌드를 무조건 반복하지 않는다.

허브 루트에서 실행 가능한 기존 검사 예:

```bash
python3 -m unittest test.test_data_grid_keyboard_nav test.test_inbound_new_receipt_grid_keys
```

위 두 테스트는 확인 당시 `unittest` 기반이며 제품 소스 문자열을 검사하는 정적 회귀 검사다. 동작을 재현하는 브라우저 테스트를 대체하지 않는다. 추가로 `test/test_theme_contrast_guard.py`, `test/test_dec232_grid_freeze.py`, `test/test_lookup_dialog_no_auto_select.py`, `test/test_dec202_lookup_empty_enter_popup.py` 등을 변경 범위에 따라 읽고 적합한 러너로 실행한다. 테스트를 통과시키려고 기존 요구사항을 삭제하지 않는다. 구현 방식만 바뀌어 문자열 검사가 낡았다면 행동 요구사항이 유지됨을 입증한 뒤 검사를 갱신한다.

확인 당시 프런트엔드 `package.json`에는 `test` 스크립트가 없었다. `npm test`나 Playwright·Vitest 환경이 있다고 가정하지 않는다. `tsconfig.json`은 `src/**/__tests__/**`를 제외하므로 그 안에 테스트를 추가한 경우 `typecheck` 통과만으로 테스트가 컴파일·실행되었다고 보고하지 않는다. 기존 브라우저 도구를 우선 사용하고 새로운 테스트 도입은 변경 위험과 비용에 맞춰 결정한다.

최종적으로 허브와 제품 각각에서 `git diff --check` 및 `git status --short`를 확인한다. 새 파일은 diff 출력에서 빠질 수 있으므로 별도로 내용을 확인한다.

### 수동 검증 기록표

각 행의 결과는 `통과 / 실패 / 미실행 / 해당 없음` 중 하나로 기록한다. 미실행에는 이유와 다음 실행 절차를 적는다. 아래 표를 결과 문서에 복사해 사용한다.

| ID | 조건·조작 | 기대 결과 | 결과·증거 |
| --- | --- | --- | --- |
| K01 | 일반 Enter로 헤더·행 입력 이동 | 기존 입력 순서와 전체 선택 유지 | |
| K02 | 비고의 정상 Enter | 새 행 정확히 1개, 새 행 구분에 포커스 | |
| K03 | 비고 한글 조합 중 Enter 후 정상 Enter | 첫 입력은 글자 확정만, 다음 정상 입력은 새 행 추가 | |
| K04 | 검색 팝업 ↑↓·Enter | 의도한 결과 선택, 정해진 다음 칸 이동 | |
| K05 | 자동완성·팝업 ESC | 최상위 상태 하나 취소, 배경 화면 유지 | |
| K06 | 팝업 열린 상태의 저장키 | 배경 전표 저장 요청 없음 | |
| K07 | 저장키 누르고 유지·빠른 반복·클릭 병행 | 동일 저장의 중복 요청 없음 | |
| K08 | 테스트 환경 저장 실패·재시도 | 값 보존, 잠금 해제, 재시도 가능 | |
| K09 | 신규 저장 성공 | 기존 날짜·연속 입력·거래처 복귀 유지 | |
| K10 | 그리드 방향키·문자 중간 좌우 이동 | 셀 이동과 글자 편집 규약 유지 | |
| K11 | Tab·Shift+Tab, 팝업 열기·닫기 | 모든 기능 접근, 포커스 순환·복원 | |
| K12 | 창 전환·이동·크기 변경 | iframe 재로드·입력값 초기화 없음 | |
| V01 | 변경 전후 동일 해상도·배율 | 표 행·열 정보량과 키보드 순서에 불필요한 감소 없음 | |
| V02 | 긴 제목·긴 거래처명·빈 표·많은 행 | 잘림·버튼 겹침·합계/페이저 충돌 없음 | |
| V03 | 기본 테마·사용 계정 테마 | 입력 포커스·선택 행·오류 구분 가능 | |
| V04 | 창을 좁힌 상태·스크롤·확대 | 필수 컨트롤 접근과 포커스 가시성 유지 | |

임시 화면 비교 환경으로 1366×768과 1920×1080, 100% 배율을 사용할 수 있으나 이는 사용자 장비 확정값이 아니다. 실제 사용 환경이 확인되면 그 환경을 우선한다. 스크린샷에는 개인정보·거래 데이터가 노출되지 않게 테스트 데이터를 사용한다.

### 완료 판정

- **구현 완료**: 요청 범위의 대표 조회·입력 화면 레이아웃 개선과 필요한 공통 요소 수정이 실제 코드에 반영됨.
- **자동 검사 완료**: 실행한 검사·명령·결과가 기록되고 이번 변경으로 생긴 실패가 해결됨.
- **실화면 검증 완료**: 브라우저에서 해당 화면의 시각·상호작용 결과를 확인함.
- **사용자 검증 완료**: 기존 사용자가 실제 환경에서 반복 입력을 확인함. 에이전트 자체 테스트로 대체하지 않음.
- **배포 완료**: 별도 배포 요청과 실제 배포 결과가 있을 때만 표시함.

문서 작성이나 키보드 가드 추가만으로 레이아웃 통일 완료라고 보고하지 않는다. 실행 범위 밖의 후속 항목이 있더라도 완료한 범위와 남은 범위를 정확히 구분한다.

## 결과 보고 형식

1. 변경한 화면과 공통 요소, 변경 이유.
2. 유지된 키보드 동작: 새 행 추가·검색 복귀·연속 입력 등.
3. 변경 전후 레이아웃 증거와 검증 결과.
4. 발견한 기존 문제와 이번 수정 범위 밖의 사항.
5. 후속 적용 화면·예외·미검증 항목.

### 실행 결과·인수인계 파일 템플릿

기본 결과 경로는 허브의 `docs/ui-layout-keyboard-improvement-results.md`다. 이미 있으면 기존 기록을 보존하고 실행 일시·범위를 덧붙인다. 제품 저장소만 전달된 환경이라면 접근 가능한 문서 경로를 선택해 보고한다. 허브 문서는 제품 Git에 포함되지 않으므로 두 저장소의 변경 파일을 구분한다.

```markdown
# UI 개선 실행 결과

- 실행 일시 / 담당 엔진:
- 허브·제품 경로 / 기준 커밋:
- 시작 전 기존 변경 파일:
- 이번 요청 범위 / 대표 화면:
- 브라우저·OS·IME·해상도 / 테스트 데이터 조건:

## 변경 내용
| 파일·화면 | 이전 상태 | 변경 이유·결과 | 보존한 업무 동작 |
| --- | --- | --- | --- |

## 검증
- 실행 명령·작업 디렉터리·성공/실패:
- K01~V04 결과와 증거:
- 변경 전후 화면 자료 경로:
- 기존 실패와 새 실패 구분:
- 실제 IME·사용자 검증 여부:

## 후속 작업과 재개 지점
- 완료 단계:
- 미완료 항목·이유·다음 행동:
- 변경하면 안 되는 기존 동작·예외:
- 실행 중인 프로세스가 있다면 작업자가 시작한 것만 식별:
- 구현 / 자동 검사 / 실화면 / 사용자 검증 / 배포의 개별 상태:
```

컨텍스트가 끊기면 위 기록과 현재 Git diff를 먼저 읽고 이어서 진행한다. 검증되지 않은 항목을 완료로 바꾸거나 기존 변경을 초기화하지 않는다. 이 명세 자체를 수정하는 요청과 이 명세에 따른 제품 구현 요청을 구분한다.
